# SmartExpense
A personal finance app where users can track expenses, manage budgets, receive reminders, view spending analytics, and optionally sync data with a backend.

## Account switching

Room data is not partitioned per user; the device holds one account's data at a time. When a sign-in resolves to a different user than the last one stored in `account_session` preferences, the local database is cleared before that account's categories, expenses, and budgets are pulled from Supabase. Signing back into the same account keeps the local copy.

Consequences worth knowing:

- Unsynced local changes belonging to the previous account are discarded on a switch.
- Recurring schedules and budget-alert history are stored locally only, so they are also removed when switching accounts.

## Budget sync

Budgets are backed up to Supabase alongside categories and expenses. Adds and edits are uploaded by the existing sync worker, deletions are queued and applied remotely, and the signed-in user's budgets are pulled back into Room on a fresh install or new device.

The `budgets` table must exist in the Supabase project with these columns (run this in the Supabase SQL editor):

```sql
create table if not exists public.budgets (
    id bigint generated by default as identity primary key,
    client_id uuid not null unique,
    user_id uuid not null references auth.users (id) on delete cascade,
    category_id bigint not null,
    amount numeric not null,
    start_date timestamptz not null,
    end_date timestamptz not null,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now()
);

alter table public.budgets enable row level security;

-- Safe to re-run: replaces the policy if it already exists.
drop policy if exists "Users manage their own budgets" on public.budgets;

create policy "Users manage their own budgets"
on public.budgets
for all
using (auth.uid() = user_id)
with check (auth.uid() = user_id);
```

If an earlier version of this table was created with `text`/`double precision`/`bigint` columns, drop it first (only if it has no data you need) and re-run the script:

```sql
select count(*) from public.budgets;  -- check first

drop table if exists public.budgets cascade;
```

To keep existing rows instead, convert the columns in place:

```sql
alter table public.budgets
    alter column client_id type uuid using client_id::uuid,
    alter column amount type numeric using amount::numeric,
    alter column start_date type timestamptz using to_timestamp(start_date / 1000.0),
    alter column end_date type timestamptz using to_timestamp(end_date / 1000.0);

alter table public.budgets
    add column if not exists created_at timestamptz not null default now(),
    add column if not exists updated_at timestamptz not null default now();

create unique index if not exists budgets_client_id_key
    on public.budgets (client_id);

drop policy if exists "Users manage their own budgets" on public.budgets;

create policy "Users manage their own budgets"
on public.budgets
for all
using (auth.uid() = user_id)
with check (auth.uid() = user_id);
```

The column types mirror the existing `categories` and `expenses` tables: `uuid` client/user IDs, `numeric` amounts, and `timestamptz` dates. `category_id` refers to the `categories.id` row for the same user. The unique `client_id` constraint is required because uploads use it as the upsert conflict target.

## CSV and PDF report exports

The Reports screen can export the selected date range as either transaction details or a report summary, in CSV or PDF format. Files are generated from the local Room data and can be saved through the Android Storage Access Framework or shared through the Android Sharesheet. The selected format controls the save picker MIME type and the share MIME type (`text/csv` or `application/pdf`).

Transaction CSV columns:

```text
transaction_id,expense_date,category_name,description,amount,currency
```

Summary CSV columns:

```text
section,label,value,percentage,date
```

Summary rows use the `summary` section for the date range, currency, total, count, and average. `category` rows contain category amounts and percentages, and `daily` rows contain ISO dates and daily totals.

Dates are ISO 8601 (`YYYY-MM-DD`), amounts are plain decimal strings with two fraction digits, and the app's PHP currency is exported explicitly. Text fields are CSV-escaped, and values that could be interpreted as spreadsheet formulas are prefixed with an apostrophe in the generated file only.

PDF exports use the same report calculations and include a title, selected date range, and currency. Transaction PDFs contain a paginated table with transaction ID, date, category, description, amount, and a total row. Summary PDFs contain totals, transaction count, average expense, category breakdown with percentages, and daily spending. PDF rendering happens in the Android feature layer with `android.graphics.pdf.PdfDocument`; the domain provides platform-agnostic report data.

Export filenames follow these patterns:

```text
smartexpense_transactions_2026-01-01_2026-01-31.csv
smartexpense_report_2026-01-01_2026-01-31.csv
smartexpense_transactions_2026-01-01_2026-01-31.pdf
smartexpense_report_2026-01-01_2026-01-31.pdf
```

Share files live in the app's private cache directory and are exposed only through a restricted `FileProvider` content URI. The app never shares a `file://` URI.
